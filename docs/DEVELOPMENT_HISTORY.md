# ComicForge AI 开发演进与问题复盘

## 1. 文档目的

ComicForge AI 从离线 Mock 原型逐步发展为可组合文本模型、审查模型和图片模型的漫画制作平台。开发过程中积累了大量关于结构化输出、真实 Provider、ComfyUI、角色一致性、漫画排字和前端交互的排查记录。

本文只保留具有长期价值的内容：

- 为什么采用当前架构；
- 遇到过哪些代表性问题；
- 问题的根本原因、解决方法和实际成效；
- 哪些问题已经解决，哪些仍受模型或外部环境限制；
- 后续工作应按什么优先级继续。

临时 Git 状态、某次会话恢复命令、已经失效的文件数量和重复启动说明不再保留。当前运行方式以根目录 `README.md` 为准，当前任务状态以 `TASKS.md` 为准。

## 3. 架构演进



### 3.1 从单体 Demo 到分层服务

最初目标是尽快验证“故事输入到漫画 PNG”能否成立，因此先用确定性的 Mock Provider 打通：

```text
故事输入 → Mock 分镜 → Mock 图片 → 本地排字 → 页面组合 → PNG
```

原型证明了数据结构、页面布局和 UI 流程可行，但也暴露出两个问题：真实模型协议差异很大，且把模型调用写进 UI 会使每次换模型都改动主流程。随后项目形成稳定分层：

- `ui.py` 负责输入、状态展示和回调连接；
- `service.py` 负责编排创作、审查、生图、保存和局部重生成；
- `schemas.py` 负责跨模块数据契约；
- `models/` 封装各 Provider 的协议与错误；
- `prompts/` 集中管理模型指令；
- `bubble_renderer.py` 和 `layout.py` 负责本地漫画制作。

这一结构使文本、审查和图片模型能够分别替换，也让真实 Provider 失败不会破坏排字与导出模块。

### 3.2 从自由文本到可信项目数据

真实大模型不会稳定地逐字遵守 JSON 示例。项目逐步建立以下边界：

1. 提取纯 JSON 或 Markdown JSON 代码块；
2. 只对已知、安全的字段别名和常见类型做归一化；
3. 使用 Pydantic 验证角色、分镜、文字项、位置枚举和数量关系；
4. 对疑似截断、缺字段和业务校验失败分别报错；
5. 修复次数有明确上限，不能无限重试；
6. 审查稿失败时保留已验证初稿；
7. 所有回退、未应用审查和真实 Provider 都必须对用户可见。



### 3.3 从“生一张图”到图片 Provider 平台

图片层统一使用 `ImageGenerationRequest`、`ImageGenerationResult` 和 `ImageProviderCapabilities`。Provider 声明是否支持 seed、参考图、mask、negative prompt 和任意尺寸，服务层在请求前拦截不支持的参数。

远程 URL 或 Base64 输出必须经过下载大小、Content-Type 和 Pillow 解码检查；ComfyUI 输出通过任务提交、历史轮询和 `/view` 下载归一化为同一种本地图片记录。这样页面排版无需了解图片来自哪个厂商。

## 4. 文本生成与审查问题复盘


| 问题表现                                | 根本原因                                   | 改进方法                                            | 改进成效                        | 当前边界                                      |
| ----------------------------------- | -------------------------------------- | ----------------------------------------------- | --------------------------- | ----------------------------------------- |
| Ollama 状态正常但生成长时间无结果                | 状态检查和模型生成使用同一短超时；小模型首轮加载慢              | 分离连接、状态、生成和审查超时                                 | 能区分“服务不可达”和“生成较慢”           | 本地速度仍受 CPU/GPU、上下文和模型大小影响                 |
| JSON 尾部缺失或 `done_reason=length`     | 输出 token 不足或故事过长                       | 识别截断原因；提供独立 token/context 配置；修复重试时可提高预算         | 不再把截断误报成网络超时                | 8–20 格长项目仍需更强模型或更大预算                      |
| `panels`、`story`、`characters` 等字段缺失 | 模型返回摘要、局部对象或审查 patch                   | 初稿保持必要字段严格；审查稿允许从已验证初稿继承未修改内容                   | 审查的冗余字段遗漏不再毁掉有效初稿           | 无法确定对应关系时仍拒绝合并                            |
| 审查稿 panels 数量与 `panel_count` 不一致    | 审查模型只返回修改过的分格                          | 按稳定 `sequence` 合并部分 panels；未返回分格继承初稿            | 局部审查可以安全应用                  | sequence 缺失、重复或越界时 `review_applied=false` |
| 子镜头缺 `visual_description`，位置写成自由文本  | 不同模型对嵌套 schema 的服从方式不同                 | Provider 无关的紧凑分镜归一化；只映射明确可恢复的枚举                 | DeepSeek 等模型的合法紧凑输出可以进入统一结构 | 不猜测语义不明的位置或画面内容                           |
| `speaker_anchor.y` 返回字符串            | 模型把数字坐标写为文本                            | 对可安全转换的数值进行类型归一化，再交给 Pydantic                   | 减少无意义的整稿重试                  | 非数字内容仍明确报错                                |
| 中文项目出现英文对白或旁白                       | 图片 Prompt 必须英文的要求污染了可见文字               | 将 `image_prompt` 与可见漫画文字分别约束；对错误语言文字做最小索引修复     | 可见文字修复不必重新生成完整项目            | 小模型连续修复失败时仍停止并说明原因                        |
| 修复稿缺少有效 sequence                    | 模型返回的文字 patch 无法对应原分格                  | 修复请求只包含目标索引；校验 sequence/index 后局部应用             | 避免错误覆盖其他分格                  | 不能可靠定位时拒绝修复                               |
| 审查耗时可达到数分钟                          | 审查请求重复携带图片 Prompt 和非叙事字段，且沿用 300 秒生成上限 | 发送紧凑叙事快照；设置独立 `TEXT_MODEL_REVIEW_TIMEOUT`       | Demo 中审查失败更快释放，并保留初稿继续生图    | 审查模型质量与速度仍由具体服务决定                         |
| 模型组合一换就出现不同错误                       | 各模型输出习惯、上下文、token 和协议兼容程度不同            | 统一 schema 边界和 Provider 适配；错误分类；先做文本 Mock 图片组合测试 | 换模型不再要求修改 UI 或主流程           | “已适配”不等于所有模型都能稳定服从同一复杂 schema             |




### 4.1 审查状态的准确含义

- `script_reviewed=true`：项目运行过审查流程。
- `review_applied=true`：审查修订稿通过校验并实际覆盖或合并到初稿。
- “审查未应用”：初稿仍可用，但修订稿因为超时、缺字段、数量错误或无法安全合并而被拒绝。

这三个状态不能相互替代。前端和 `project.json` 都应保留原因，避免把“请求过审查模型”误写成“审查成功”。

## 5. 云端图片 Provider 问题复盘


| 问题表现                                 | 根本原因                                                 | 改进方法                                        | 改进成效                                | 当前边界                    |
| ------------------------------------ | ---------------------------------------------------- | ------------------------------------------- | ----------------------------------- | ----------------------- |
| API Key 401/403                      | Key 无效、站点不匹配或进程未重启                                   | 分开配置 endpoint/Key；状态检查脱敏；修改 `.env` 后重启      | 鉴权问题与生成问题可以区分                       | 接收源码的人仍需使用自己的账户配置       |
| SiliconFlow 中国站与国际站混用                | 不同站点账户和域名并非互通                                        | 先核对站点，再调用模型列表验证目标模型                         | 已验证国际站 Key、`GET /v1/models` 和目标模型存在 | 余额为 0，不能写成真实收费生图验收      |
| Recraft 报 seed 不支持                   | 通用请求把 seed 发送给不支持该参数的 Provider                       | 通过能力声明决定 UI 和请求字段                           | Recraft 四格不再因 seed 整批失败             | 不能依赖 seed 复现 Recraft 结果 |
| 多格全部 ConnectTimeout                  | 网络或平台暂时不可达，不是分镜结构错误                                  | 将连接、读取和生成错误分类；仅瞬态错误有限重试                     | 用户能看到具体 Provider 和失败分格              | 云端网络和平台 SLA 不受项目控制      |
| URL/Base64 响应格式各异                    | 厂商返回结构不同                                             | Provider 内归一化，公共下载层验证图片                     | 排版层只接收本地有效图片                        | 新 Provider 仍需单独实现协议测试   |
| Gemini `/images/generations` 不支持目标模型 | Gemini 图片模型通过 `generateContent` 而非传统 Images endpoint | 增加 `interactions` 与 `generate-content` 两种模式 | 已完成无参考、单参考和四格真实闭环                   | 第三方网关未必完整支持官方所有参数       |
| Gemini 请求成功但画幅未按页面变化                 | 图片大小档位与宽高比是两个不同参数，兼容网关可能忽略字段                         | 根据分格宽高计算最近宽高比，并按网关模式发送正确配置                  | 接口已能表达目标比例                          | 仍需以实际返回尺寸验收，不能只看请求体     |
| 超时后自动重试可能重复扣费                        | 按次网关对失败和超时的计费规则不透明                                   | Gemini 默认 `GEMINI_MAX_RETRIES=0`            | 降低隐式重复扣费风险                          | 是否扣费最终以平台账单为准           |




## 6. ComfyUI 本地工作流问题复盘



### 6.1 服务、模型和 Workflow


| 问题表现                  | 根本原因                               | 改进方法                                  | 成效                   |
| --------------------- | ---------------------------------- | ------------------------------------- | -------------------- |
| 连接不上 `127.0.0.1:8188` | ComfyUI 未启动或端口不同                   | 先检查 `/system_stats`，再进入生成             | 避免等待数分钟后才发现服务未启动     |
| 网页工作流能运行，API 提交失败     | 使用普通 UI Workflow JSON              | 从 ComfyUI 导出 API Format JSON          | `/prompt` 可以接收正确节点字典 |
| Prompt、尺寸或 seed 不生效   | 节点 ID 配错或工作流已变更                    | 依据 `class_type` 和连线确认节点；环境变量配置        | 工作流可动态替换，不修改源 JSON   |
| checkpoint 或节点缺失      | 仓库只含 Workflow，不含大型权重和自定义节点         | 文档明确外部依赖；先在 ComfyUI 手动运行              | 源码可迁移，模型环境由使用者管理     |
| 任务列表显示已生成，应用仍超时       | 某一格真实耗时超过 300 秒或 history 终态未及时被轮询到 | 记录逐格耗时和 prompt ID；检查队列、终端、history 和输出 | 能区分慢任务、卡队列和下载失败      |
| 第四格突然比前三格慢十倍          | 模型/显存状态、首次或再次加载、系统换页、队列或复杂采样波动     | 完全重启 ComfyUI、清空旧队列、并发设为 1、监控单格状态      | 重启后可恢复正常样本速度         |




### 6.2 参考图与角色一致性

早期曾自动把第一张剧情分格当作后续角色参考。真实测试证明，这会把第一格的姿势、背景、人物占比和特写构图一并带入后续画面，因此该策略被废弃。

随后形成当前规则：

1. 使用者显式上传干净角色参考图；
2. 参考图按 Story Bible 角色顺序绑定；
3. 每格根据实际出场角色筛选参考图；
4. 单人近景或中景才启用当前单 IPAdapter 入口；
5. 多人、远景、航拍、环境或群像暂时禁用全图参考，避免特征互相污染；
6. 启用参考图时，最终 Prompt 不再重复冲突的发型、服装和配色，而强调保持参考人物身份，只改变动作、表情、场景和镜头；
7. `project.json` 记录 `reference_count`、`reference_character_names` 和最终 Prompt。

这一改进解决了“明明使用哪吒参考图，Prompt 却要求红色短发蓝袍”的直接冲突，也让是否真正传入参考图可以验收。但单个全局 IPAdapter 不能可靠锁定多人同框的独立身份，角色一致性仍未彻底解决。

## 8. 前端与错误可见性演进

- 将创作设置集中到侧栏，主区域按“状态—画布—分镜—语言—项目”组织。
- 文本生成与收费生图分为两个阶段，同时保留明确的一键模式。
- 只展示注册且满足配置条件的 Provider，减少无效选项。
- 状态卡展示请求 Provider、实际 Provider、模型、耗时、错误和 fallback。
- 参考图上传区支持批量导入、粘贴、滚动列表和拖动排序；删除了不稳定的额外上下移选择器。
- 错误不再只表现为无限 `processing`；终端保留结构摘要，前端提供用户可读原因。
- 漫画格数由分镜项目统一控制，页面布局不再另行假定四格或八格。

前端仍有两个明确未完成项：画布上的气泡直接拖拽，以及生成队列中“排队、采样、下载、排版”的逐格实时状态。

## 9. 工程化、测试与验收演进

项目将验证分为不同层级：


| 验证层级           | 证明什么                                 | 不能证明什么                   |
| -------------- | ------------------------------------ | ------------------------ |
| Ruff           | 静态代码规范                               | 运行时逻辑和真实服务可用性            |
| pytest         | schema、解析、回退、Provider 假协议、布局和 UI 回调  | 真实 Key、余额、网络和模型效果        |
| compile/import | Python 语法和应用可加载                      | 真实生成成功                   |
| 严格 smoke test  | 一个真实 Provider 能返回并保存有效图片，且没有 Mock 回退 | 多格稳定性和角色一致性              |
| 手动项目验收         | UI、真实模型、排字、导出和项目记录组成完整闭环             | 所有其他 Provider 或其他机器也自动可用 |


开发中出现过网络中断、模型不可用和 `thread not found`。这些是开发工具会话问题，不属于 ComicForge 运行错误。恢复工作的正确方式是重新核对 `AGENTS.md`、`TASKS.md`、`README.md`、Git 状态与 diff，并以代码、测试和项目 JSON 为事实来源。本次文档整理后，不再保留专门的会话交接文件。

## 10. 已验证能力与事实边界



### 已形成闭环

- Mock 文本与图片离线流程；
- Ollama 本地文本真实生成记录；
- OpenAI-compatible 文本真实调用记录；
- DeepSeek 文本初稿与审查真实项目记录；
- Recraft 多次真实图片生成及四格无回退记录；
- ComfyUI 严格单图和多格无回退记录；
- Gemini 无参考、单参考和四格真实生成记录；
- 本地气泡、页面组合、PNG/PDF/JSON 导出；
- 项目重载、单格重生成和版本回退。



### 不能扩大表述

- SiliconFlow 只完成鉴权、模型列表和目标模型存在性验证，未完成收费生图验收；
- OpenAI Images、Together 和 fal 已适配但尚未完成项目级真实生成验收；
- 角色一致性得到改善，但没有彻底解决；
- 多页数据结构已预留，但完整多页 UI 和整册导出尚未验收；
- 当前没有公网部署、用户系统或多人协作闭环。

# ComicForge AI 第三阶段漫画质量改造进度报告

> 记录目标：用于后续汇报、演示和继续开发。本文不仅记录最终功能，也记录真实链路
> 验证过程中暴露的问题、定位过程、解决方案、优化原因和可观察效果。

## 1. 阶段背景与真实链路里程碑

本阶段开始前，项目已经首次跑通完整真实链路：

```text
Ollama qwen3:4b 生成故事和分镜
→ Recraft 生成四张真实无文字图片
→ Pillow 本地进行漫画排字（编号仅作为可选调试项）
→ 自动排版
→ 导出 comic.png、comic.pdf 与 project.json
```

这次验证证明 Provider 2.0 的文本、图片、回退、并发、持久化和排版边界可以协同
工作。但真实成品也暴露出两个不同层次的问题：

1. 工程兼容问题：Ollama 长生成超时、Recraft 不支持 Seed、宽高默认值不合法。
2. 漫画质量问题：剧本事实/因果不稳定，文字像底部字幕条，图片没有为气泡预留空间，
   角色一致性不足，也没有漫画内容语言选项。

因此本阶段目标从“能生成”转向“先确认正确剧本，再生成具有漫画气泡和构图意识的成品”。

## 2. 优化与故障处理时间线

| 问题或优化 | 为什么需要处理 | 根本原因 | 解决方法 | 实际效果 |
|---|---|---|---|---|
| Ollama 状态可用但正式生成超时并回退 Mock | 状态检测成功不代表长文本生成能在短读取超时内完成 | 连接超时和生成读取超时共用较短配置；Qwen3 thinking 增加响应时间 | 分离连接/生成超时，生成默认 300 秒；API 顶层 `think=false`，旧接口回退 `/no_think`；细分连接、HTTP、模型不存在、生成超时 | 本机 qwen3:4b 约 15.04 秒完成结构化方案，`api_think_false`，未回退 Mock |
| 漫画排字改造后第一步连续固定在 300 秒超时 | Ollama 状态检测成功，但 Gradio 的初稿请求始终不能返回 | 启动 Gradio 的终端环境让 `127.0.0.1` 请求经过系统 HTTP 代理；绕过代理后又发现默认 `8192/16384` 输出/上下文预算会使 qwen3:4b 的普通四格生成非线性变慢 | 文本 HTTP 层对 localhost、全部 IPv4/IPv6 loopback 强制 `trust_env=false`，远程 Provider 仍保留代理；普通默认预算降为经实测的 `4096/8192`，长故事仅在明确截断时按需调高；保留 300 秒生成兜底 | 故意配置失效代理时仍能访问 Ollama；单格结构化初稿 20.90 秒、四格初稿 35.21 秒、四格“初稿 + 自动审查”73.31 秒完成，4 格且 `script_reviewed=true`，均使用 `api_think_false` |
| 图片宽高默认值导致 Provider 参数问题 | 图片 Provider 对尺寸格式和最小值有明确限制 | UI 与统一请求的空值/默认值语义不一致 | UI 使用合法 1024×1024 默认值；Schema 成对校验宽高且限制 64–8192 | 单图与完整漫画采用稳定合法尺寸 |
| Recraft 单图成功、四格却全部报 Seed 不支持 | 完整流程与 smoke test 的参数路径不同 | Gradio 将 `0` 当成真实 Seed；服务在确认 Provider 能力前统一计算 `seed + panel_index` | `0/空值 → None`；切换 Recraft 时清空并禁用 Seed；逐次调用按实际 Provider 能力附带 Seed；明确正整数不兼容仍报错 | Recraft 四格能够进入 4 次 HTTP 请求，均不含 `seed`；SiliconFlow 等仍收到逐格递增 Seed |
| 一次点击直接消耗四张 Recraft Units | 用户无法在付费生图前发现事实、因果或台词问题 | 文本与图片被一个 UI 回调串成不可确认的单步流程 | 拆为“生成并审查分镜”与“确认分镜并生成漫画”；中间提供可编辑表格 | 第一阶段只调用文本模型；用户确认后才调用图片 Provider |
| 历史题材出现人物时间线和身份错误 | 合法 JSON 不等于正确故事 | 原提示词只强调结构，没有建立统一事实与时间线约束 | 新增 `story_bible`；初稿后用同一文本 Provider进行逻辑审查和自动修订；审查身份、时间线、因果、连续性、动作可视化和不确定事实 | 明显降低人物跨时间线、身份错置和关键因果缺失风险；不承诺小模型绝对事实正确 |
| 特洛伊木马等原著题材自动审查后仍可能失真 | 小型本地模型无法保证掌握或准确复述所有原著，逐格表格又不适合用户讲完整故事 | 自动审查只能依据模型已有知识；缺少用户提供的权威故事依据和整篇重做入口 | 新增多行“正确的故事细节”输入和“重做完整分镜”按钮；将用户说明作为最高优先级约束传给统一 Text Provider，重建概要、Story Bible、角色、全部分镜和提示词，并将原文保存到 `user_story_guidance` | 用户可反复纠正整段故事且全程不调用图片 Provider；表格只承担最终单格微调，付费生图边界不变 |
| 用户提交故事修改后 Ollama 报“JSON 第 142 行无效” | 文本模型实际完成了请求，但输出无法进入 Pydantic 校验，用户只能看到重做失败 | 重做提示词同时包含完整旧项目、用户长说明和完整输出要求；修复时又回填最多 12000 字符的残缺 JSON；要求模型复制含换行/引号的用户原文进一步增加转义和截断风险 | 旧项目改为紧凑请求上下文并附单格 Schema 示例；`user_story_guidance` 由程序在校验后写入，不要求模型复制；修复从干净上下文重生成；安全接受 JSON 字符串内的原始换行；Ollama 使用低温度并识别 `done_reason=length`，预算默认 `4096/8192` 且可在确实截断时按需调高 | 多行、中文引号故事说明可安全保留；修复请求显著缩短；若仍截断会明确提示调整 `OLLAMA_NUM_PREDICT`/`OLLAMA_NUM_CTX`，不再只报告模糊行列错误 |
| 修改故事后重做分镜直接报 Ollama 输出达到长度上限 | 真实 `qwen3:4b` 已明确返回 `done_reason=length`，但 Provider 在解析循环之前立即抛错，已有自动修复机会无法执行 | 完整重做需要同时输出故事、人物、Story Bible、全部分镜和绘图提示词；默认 `4096/8192` 对较长故事可能不足，永久提高默认预算又会拖慢普通生成 | 将重做 Schema 改为紧凑 JSON，并限制各说明字段的合理长度；检测截断后不使用残缺内容，而是从原始上下文自动重做一次，将本次预算临时提高到最多 `8192/16384`；第二次仍截断才提示修改环境变量 | 普通请求继续使用较快默认预算；长修订获得一次自动恢复机会。Mock HTTP 验证第一次截断、第二次完整返回时能成功进入结构校验，且第二次请求实际使用扩大后的预算 |
| 第一轮人工修订后无法自然地继续修改 | UI 只有一个故事说明框，看不到历史；新意见会覆盖上一轮约束 | 项目只保存一个 `user_story_guidance` 字符串，没有结构化修订轮次 | 新增 `RevisionTurn` 与 `revision_history`；每轮都以最新 ComicProject 为基础，旧约束与本轮追加意见同时进入提示词，程序累积保存后再更新状态 | 可连续提交第二、第三轮修改且不调用图片 Provider；项目详情和 JSON 都能追溯每轮意见 |
| 标题“特洛伊木马的暗影”生硬模板化 | 标题由小模型一次决定，用户在付费生图前无法单独修改 | 提示词没有候选标题和反模板词约束，UI 没有最终标题输入 | 要求生成 3 个具体候选标题并避免无关“暗影/命运/传奇”套词；新增可编辑最终标题框 | 用户可选择或直接重写标题，最终排版使用人工确认值 |
| 气泡尾巴像贯穿画面的白色标注线，旁白框过大 | 成品看起来像演示标注而不是漫画 | 尾巴直接连接气泡与远处人物锚点，未限制长度；旁白与对白共用尺寸上限 | 尾巴最大约 52px，只表示方向；没有人物锚点时不画；缩小旁白宽高和字号，自动精简过长对白/旁白 | 离线三语言预览中长白线消失，气泡不显示说话者姓名，旁白更轻量 |
| 固定 2×2 无法表达高潮、条漫或一格多镜头 | 故事节点、镜头、漫画格和页面被绑定为同一概念 | 只有双列网格排版，Panel 没有重要度和内部镜头结构 | 新增 `layout_mode`：传统漫画页、竖向条漫、规则网格；5/6 格传统页可按 `importance` 分配大小，四格保持稳定 2×2；Panel 新增 `composition/subshots` 支持 inset、横/纵分割和 montage | 同一套故事可在三类页面形式间选择；必要时一个 Provider 请求可表达主画面加辅助镜头，不强迫每格拆分 |
| 用户希望选择是否人工介入 | 两阶段流程安全但无法满足快速自动直出 | UI 只有人工确认路径 | 新增人工审查/自动直出选择；自动按钮明确警告图片额度并由 service 连续执行文本审查和图片生成 | 默认仍保护 Units，用户主动选择自动模式时可一键完成 |
| 自由页首次预览把靠边气泡裁掉 | 不等宽格框会改变原始 3:2 分格宽高比 | 已经绘制气泡的分格使用 `ImageOps.fit` 强制裁切，边缘文字随画面一起被裁掉 | 阶段性改为完整缩放前景和模糊背景补边；随后根据真实四格反馈，仅在非四格异形模板保留完整缩放，四格改为等幅轻裁切铺满 | 该阶段性方案保住了文字，但真实图暴露出模糊补边不美观，最终方案见下一项 |
| 四格自由页出现大块模糊空白，画框大小变化没有叙事必要 | 四张同画幅图片被 importance 强制放入 64/36 宽度格框，`contain` 后只能用模糊背景补边 | 自由页算法把“可变格框”无条件应用到最常见四格，且文字已提前绘制使裁切困难 | 四格传统页固定为等宽等高 2×2；使用轻微居中 cover 裁切铺满格框；5/6 格等真正需要变化时才保留大小格模板 | 新离线 1536×1120 样张四格全部填满，无模糊横条/竖条，格框比例一致 |
| 默认等幅四格稳定，但用户需要“四个小格＋两个横向长幅”等主动设计 | 自动大小格和用户明确设计是两种需求，不能为了修复随机变形而永久禁止大小格 | 旧 `layout_mode` 只有固定模板，没有可持久化的画框顺序、合法性校验和按格画幅 | 新增 `custom_page` 与 `CustomPanelFrame`；用户点选任意画框后可在其后插入或直接删除；方形/竖幅同类成对，横幅独占一行；生成前校验，失败时不调用图片 Provider；每格优先按目标比例生图，不支持时才选最近比例 | 默认自动排版完全不变；Mock HTTP 验证 Recraft 方格请求 `1:1`、宽幅请求其原生支持的 `3:2`，输出无残缺行和模糊补边；界面显示逐格实际请求画幅 |

## 3. 新的生成架构

```text
用户主题、风格、格数、内容语言
        │
        ▼
TextModelProvider 生成初稿 JSON
        │
        ▼
同一 TextModelProvider 审查 story_bible、事实、时间线、因果、连续性和台词
        │
        ▼
修订后的 ComicProject → Gradio 可编辑分镜表格
        │ 故事不合格：用户补充事实/原著情节
        ├──────────────→ TextModelProvider 重做并校验全部分镜 ──┐
        │                                                       │
        └───────────────────────────────────────────────────────┘
        │ 用户确认（真实图片费用边界）
        ▼
每格统一角色设定 + 当前动作 + 角色位置 + 气泡负空间 + 禁止文字
        │
        ▼
ImageProvider 生成无文字画面
        │
        ▼
本地 Bubble Renderer 绘制对白/思考/旁白/拟声词
        │
        ▼
compose_comic → comic.png + comic.pdf + project.json
```

旧的一键 `generate_with_status()` 仍保留用于兼容；新版 UI 使用：

- `generate_script_with_status()`：只生成、审查、修订剧本。
- `redesign_script_with_guidance()`：依据用户自然语言故事说明重做并校验整套分镜，不生成图片。
- `render_confirmed_project()`：只对已经确认的项目调用图片 Provider。

## 4. 数据结构升级

### 4.1 `StoryBible`

记录时间、地点、人物准确身份、固定外观/服装、动机、关键道具、因果时间线和统一
视觉风格。所有分格必须遵守这份临时“故事圣经”。

### 4.2 `ComicTextItem`

```json
{
  "type": "speech",
  "speaker": "角色名",
  "text": "简短台词",
  "preferred_position": "top_left",
  "speaker_position": "bottom_right",
  "speaker_anchor": {"x": 0.75, "y": 0.7}
}
```

支持 `speech`、`thought`、`narration`、`sfx`。旧 `dialogue`、`narration` 继续
保留，载入时自动迁移；新结构为空时不会破坏旧文件。

### 4.3 分镜构图字段

- `narrative_role`：本格的建立、发展、转折或结果作用。
- `character_positions`：角色大致构图位置。
- `reserved_bubble_regions`：生图前预留的低细节区域。
- `render_warnings`：台词过长、发生可见省略等警告。

### 4.4 项目字段

- `content_language`：`zh-CN`、`en`、`ja-JP`，旧项目默认 `zh-CN`。
- `story_bible`、`review_notes`、`script_reviewed`。
- `bubble_theme`：当前气泡主题。
- `lettering_style`：`immersive`、`classic` 或 `minimal`，旧项目默认迁移为沉浸式。
- `show_panel_numbers`：是否显示调试编号，成品默认 `false`。
- `ComicTextItem.presentation`：`auto/bubble/text_only/caption/burst`，允许后续逐项控制。
- `localizations`：按语言保存标题和每个 `text_item` 的译文，切回已生成语言时不调用模型。
- `custom_layout`：按分镜顺序保存 `square/portrait/landscape/wide` 画框；仅在
  `custom_page` 模式下参与排版，重新载入项目仍可恢复。

## 5. 气泡定位与尾巴算法

1. 文本先按语言换行：英文以单词为单位；中文/日文以字符为单位，并尽量避免结束
   标点出现在新行开头。
2. 字号从最大值逐级缩小到最小值，计算文字实际边界、padding 和气泡面积。
3. 以分镜规划位置为第一候选，再尝试七个区域；综合已放置文字相交面积与底图边缘密度，
   优先选择不重叠、低细节的负空间。
4. 所有矩形经过 panel 安全边距 clamp，不能越出当前分格。
5. speech 的尾巴尖端优先使用 0–1 归一化 `speaker_anchor`；没有锚点时根据
   `speaker_position` 推导。尾巴根部选择气泡上、下或侧边最接近人物的一点。
6. 沉浸式 speech/thought 使用轻微不规则、半透明手绘轮廓；narration 默认直接使用随底图
   明暗自动反转的无框描边字；sfx 使用放大、双描边和轻微旋转。`classic` 仍保留旧规则样式。
7. 普通气泡宽度小于分格约 43%，高度有上限，不再生成横跨整格的底部条。
8. 最小字号仍放不下时显示省略号，并把明确警告写入 `render_warnings`；默认启用的
   自动缩短会先压缩过长对白，同样记录警告，不会静默处理。

9. 左上角分格编号不属于成品文字，默认不绘制；前端只提供调试开关。

当前不使用人脸识别模型。遮挡规避依赖“剧本规划角色位置 + 生图预留负空间 + 已放置
气泡重叠评分 + 底图边缘复杂度”。边缘评分能避开一部分繁忙区域，但不能替代人物/面部检测。

## 12. 生图后切换语言：文字项数量不一致

### 12.1 现象

真实使用 Ollama `qwen3:4b` 切换成品语言时，文本模型已经返回了翻译结果，但第 2 格的
翻译文字项数量与原项目不一致，校验阶段因此终止。典型错误为：

```text
第 2 格翻译文字项数量与原项目不一致
Ollama 本地模型 漫画文字翻译无法解析
```

这不是图片 Provider 超时，也不是语言切换按钮没有触发；失败发生在翻译 JSON 返回后的
结构校验阶段。原协议要求模型按 `panels[].text_items[]` 数组原样返回，小型本地模型有时会
把同一格的对白、旁白或拟声词合并，或者拆成额外条目。数组长度一旦变化，系统无法安全判断
译文应该写回哪个气泡，因此不能直接接受结果。

### 12.2 解决方法

- 为每条可见文字分配稳定 ID，例如第 2 格第 2 条文字为 `P2-I1`。
- 翻译请求改为 `{title, texts: {ID: 译文}}`，明确禁止新增、删除、合并、拆分或重命名 ID。
- 解析器严格检查 ID 集合，再按原项目顺序把译文写回对应气泡；视觉描述、角色、图片和排版
  均不改变，也不会重新调用图片 Provider。
- 保留旧版 `panels[].text_items[]` 响应兼容，避免已有 Provider 或缓存格式立即失效。
- 首次结果仍不合格时，基于原始项目发起一次干净修复请求，并把缺失 ID 明确告诉模型；不会
  把结构错误的译文当成成功结果，也不会静默丢失文字。

### 12.3 自动化验证

新增 Mock HTTP 回归覆盖：第一次模拟 Ollama 合并第 2 格文字导致数量错误，第二次按稳定 ID
完整返回，最终成功翻译且每格文字项数量与原项目完全一致。测试不访问真实 Ollama，不调用
图片 Provider，也不消耗图片额度。真实 `qwen3:4b` 的最终效果仍需重启应用后人工切换语言验收。

## 13. 收尾阶段新增问题与处理记录

### 13.1 漫画画布出现白色、灰色交错区域

**现象：** 右侧漫画画布、预览模式和底部说明中出现不连续的灰色横条；多次只修改组件本身
后仍有残留。

**根本原因：** Gradio 会在 `Group`、`Radio`、`Image` 和 `Markdown` 外动态生成多层包装
容器。早期 CSS 只覆盖 `.form`、`.block`、`.wrap` 等内部节点，实际读取主题次级背景色的
外层 `div/gap` 没有命中；不同 Gradio 版本生成的附加类名也不稳定。

**解决方法：** 将修复限制在 `.cf-canvas-shell` 局部作用域，统一覆盖画布直接子层及包含
预览模式、图片组件和说明组件的祖先包装层，同时设置局部背景变量为白色。避免全局修改
Gradio 主题，防止影响侧栏、按钮和其他组件。

**效果：** 漫画画布、预览工具栏、图片空状态和说明区域形成连续白色表面，原有输入框边界、
按钮和紫色选中态仍保留。

### 13.2 画布变白后，选中的预览方式文字消失

**现象：** 点击“整页预览”或“放大阅读”后，只能看见紫色圆点，选中文字变成白色并消失。

**根本原因：** 为消除灰色残留时误将 `#cf-preview-mode label` 强制设为白底；Gradio 选中态
仍把文字设为白色，最终形成白字白底。

**解决方法：** 撤销对交互 `label` 的背景覆盖，只统一非交互包装层。让单选按钮继续使用
Gradio 自身的选中/未选中样式。

**效果：** 选中项恢复紫底白字，未选中项保持白底深色字，同时不重新引入灰色横条。

### 13.3 一键生成时 OpenAI-compatible JSON 缺少 `story/characters`

**现象：** 文本接口返回合法 JSON，但解析时报“模型 JSON 缺少字段：characters, story”，
一键流程在图片调用前终止。另一次“主题为空”经复核属于用户未输入主题，不作为代码故障。

**根本原因：** 部分兼容模型虽然返回了对应内容，却使用 `summary`、`synopsis`、
`story_outline`、`character_profiles` 或 `cast` 等常见别名；严格解析器只接受协议规定的
`story` 和 `characters`。

**解决方法：** 在 JSON 提取后、Pydantic 校验前增加有限白名单归一化。只映射语义明确的
常见英文/中文别名，不凭空补写真正缺失的内容；归一化后仍执行全部必填字段、类型、分镜数量
和连续序号校验。字段确实缺失时继续使用现有干净重试及显式 Mock 回退策略。

**效果：** 含常见字段别名的真实 Provider 输出可直接进入统一 `ComicProject`；新增回归测试
后完整测试数由 129 增至 130。

### 13.4 Recraft 六格全部出现 `ConnectError/ConnectTimeout`

**现象：** 文本分镜已经成功，但人工确认生图和一键生图均可能在 Recraft 阶段失败；六格分别
在约 5–10 秒连接阶段报错。此前同一 Provider 曾成功跑通四格真实链路。

**定位证据：** 配置的 endpoint 与 Recraft 官方接口一致，DNS 能解析
`external.api.recraft.ai`，但故障时 `Test-NetConnection ... -Port 443` 返回 `False`，
`curl -I` 返回 `Could not connect to server`。错误发生在收到任何 HTTP 状态码之前，因此与
Key、余额、模型参数、Seed、提示词或图片响应解析无关，也不会形成一次成功的付费生图请求。

**处理思路：**

- 不把外部网络不可达伪装成 Provider 成功，也不在严格模式中自动混入 Mock 图片。
- 用 `curl -I --connect-timeout 10 https://external.api.recraft.ai/v1` 检查 HTTPS；返回任意
  HTTP 状态码才代表链路真正可用，单次 TCP 探测为 `True` 不足以证明 TLS/HTTP 稳定。
- 网络不稳定时将逐格并发保持为 1；切换网络或使用真实运行中的代理后再验收。
- 若要求不中断演示，可显式启用 Mock 回退，但界面必须展示回退分格和原因。

**当前边界：** 这是外部运行环境问题，无法仅靠增加连接超时解决。项目已具备连接错误分类、
指数退避、严格模式和显式回退；断点续传、只重试失败分格仍属于下一阶段候选能力。

### 13.5 将不存在的 `127.0.0.1:7890` 设置为代理后应用启动失败

**现象：** `curl --proxy http://127.0.0.1:7890` 已明确连接失败，仍设置 `HTTP_PROXY` 和
`HTTPS_PROXY` 后，Gradio 启动阶段访问自身 `127.0.0.1:7860` 也经过无效代理，最终出现
`WinError 10061`。

**根本原因：** `7890` 只是常见代理软件示例端口，本机并没有进程监听；同时未配置
`NO_PROXY=127.0.0.1,localhost`。

**解决方法：** 清除错误的 `HTTP_PROXY/HTTPS_PROXY/ALL_PROXY` 后恢复启动。只有确认代理
软件实际运行并获得真实 HTTP/Mixed 端口时才设置代理，同时添加
`NO_PROXY=127.0.0.1,localhost`，避免本机 Gradio 与 Ollama 流量走远程代理。

**效果：** 明确区分“应用代码故障”“Provider HTTP 错误”和“本机代理/路由故障”，避免通过
反复生成消耗时间或造成不必要的额度风险。
